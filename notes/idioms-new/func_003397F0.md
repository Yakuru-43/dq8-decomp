## Shared-tail null guard as `if (p == 0) { r = 0; } else {…}` and tail as `if (r != 0) { return r + off; }`: CW keeps both `beql`s
Sign: a search function whose early null-exit, its hit paths (goto/break) and its
loop exit all meet at one tail `if (r == 0) return 0; return r + off;`. Writing
the guard as `r = 0; if (p != 0) {…}` gives a plain `beqz` (no `l`) with the
zero store CSE'd above it, and the tail `if (r == 0) { return 0; }` comes out
inverted: `bnel $rN,$zero,<addiu stub>; addiu $v0,$rN,off; daddu $v0,$zero,$zero`.
The original has `beql` in both places, each carrying the target block's store
in its delay slot (`beql $aN,$zero,<tail>; daddu $rN,$zero,$zero` at the guard;
`beql $rN,$zero,<jr>; daddu $v0,$zero,$zero` then `addiu $v0,$rN,off` falling
through at the tail). CLASS structural, score ~5, size identical.
Fix: put the zero store in the guard's then arm:
`if (p == 0) { r = 0; } else { …loop…; r = 0; }` (the loop-exit `r = 0;`
statement lives at the end of the else arm), and flip the tail test:
`if (r != 0) { return r + off; } return 0;`. CW then lays the trivial then
block into the branch delay slot and uses the likely form. Same function: the
`bne` operand order follows the `==` operands — `bne $a1,$v0` wants
`if (key == *(s32 *)(e + 0x180))`, `bne $v0,$a1` comes from `load == key`
(the "write the operands in the other order" idiom, for compare branches).
