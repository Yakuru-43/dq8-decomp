## 16-byte-unit reserve calls: byte-size locals keep the unfolded `sll 4`/`sra 4` and `dsll32 4`/`dsra32 4` pairs
Sign: a function that calls `func_14E130(pool, n)` (16-byte-unit allocator) several times
with counts derived from a parameter. The original does NOT fold the *16 and /16: it keeps
`sll $s5,$v1,4` (a byte size live in a callee-saved register across the calls), converts at
each call site with a lone `sra $vN,$s5,4` + `addiu ...,1`, and the *other* count comes from
`dsll32 $v0,$s2,4; dsra32 $v0,$v0,4; addiu $s0,$v0,1` ((x<<36)>>36, 64-bit <<4/>>4).
Writing the folded argument (`func_14E130(pool, count * (rows + 2) + 1)`) drops both shift
pairs (CLASS structural). Naming an intermediate early also matters: `addiu $v0,$s1,2`
sitting **between** two independent zero-stores, with `mult` after the second, vanishes if
you inline `rows + 2` at the multiply.
Fix: declare byte-size locals and divide at the call, and name the early sub-expression as
its own statement placed where the `addiu` must land:
```c
bytes1 = count * 16;                  /* dsll32 4 / dsra32 4 at use */
bytes2 = count * wide * 16;           /* mult + sll 4 into $s5      */
out->field_04 = 0;
wide = rows + 2;
out->field_00 = 0;
...
out->field_08 = func_14E130(pool, (bytes1 >> 4) + 1);
out->field_10 = func_14E130(pool, (bytes2 >> 4) + 1);
```
(`bytes2`'s factor `wide` must be assigned before the stores so `mult` schedules after
them; CW keeps `wide` in `$v0` since its last use is the early `mult`.)
