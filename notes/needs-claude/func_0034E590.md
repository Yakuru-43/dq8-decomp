## The useful finding: the three callees take 7, 5 and 4 arguments

Call 1 sets `t0/t1/t2` (n32 args 5-7); calls 2 and 3 never touch `t1/t2`, and
call 3 never touches `t0` either. With all three declared at 7 parameters
CodeWarrior re-materialises `0xE`/`0x80`/`t0` after every call and the body comes
out 152 bytes instead of 132. Declaring them at 7, 5 and 4 parameters lands the
length exactly:

## What is left, and what I do not know

Only call 1 is ordered `a2, a1, a0`; calls 2 and 3 are `a0, a1, a2` in both
builds. So the reversal is specific to the call that has a t-register argument
whose value is **another argument's value** (`arg5 == arg1 == 1`, emitted as
`addiu $a1` + `daddu $t0, $a1`). In `asm/SLES_539.74/game_13C490.s:25-30` the
same shape appears (`daddu $a2, $a0` deferred after `a0, a1, t0, t1`) and there
the rest stays forward-ordered, so "defer the inter-arg copy" is right but does
not explain why the original also reversed `a0` and `a2`.

Tried (11 attempts, all 132 B, all with the same single swap):
`value.f` before `value.i`; a named `struct Pair`; two separate locals (moves
the float to 0x38 — wrong); `&value.i` instead of `&value`; the last two args as
one `s64` 0x800000000E (breaks it: `or $t1, $v0, $v1`); a shared `s32 one = 1`
variable; calls 1 and 2 declared `void`; `arg2` and the callee arg0 as `void *`;
and two diagnostics that drop calls (single-call builds order `a0` first, so the
reversal is not the 7-arg call by itself).

**What would fix it:** the rule that decides the order of the argument copies
for a call whose args include a copy of another arg register — apparently
something puts `&value` ahead of the `s0` copy here. If it is not reachable from
the source, the other option is a `// permuter-artifact` tag, but I would rather
know the idiom: this same "mwcc ordered the copies differently" wall cost P14
and P15 too.

New corpus evidence — the promotion rule and why it cannot fire here:
the matched debug caller `src/SLES_539.74/func_00381DF0.c` writes
`func_002D4240(temp_a0, 0x138C, 1, 1);` and gets
`addiu a2,1; addiu a1,line; daddu a0,s0; jal; daddu a3,a2` (delay slot):
mwcc **promotes the shared-constant copy to first and sinks the copying copy
(`aX <- aY`) to last** — but only when the shared pair sits inside `a0..a3`.
P16's shared pair is (arg1, arg4): arg4 lands in `t0`, across the t-register
boundary, and there mwcc does **not** promote — it keeps position order and only
defers `daddu t0,a1` past the others. Grep: no matched function in `asm/` has
`daddu $t0, $a1` at all; the call shape only exists in unmatched functions.

Permuter: was never really run on P16. From the m2c draft it scores 715+ (m2c
declares all three callees at 4 args — the 7/5/4 discovery never reaches it);
re-ran 120 s with the clean 132 B C above as `base.c`: **zero outputs**, no
improvement — statement permutation cannot reach inside a call expression, so
this wall is outside the permuter's space, same as P14/P15/P25.

Remaining idea for Claude: mwcc's call-copy scheduler looks like a list
scheduler keyed on def order; the original's `addiu a2,sp` sitting ahead of
`addiu a1,1 + daddu a0,s0` may need a *front-end* difference we cannot express
(e.g. args pre-evaluated through temporaries inside the call by a macro, or a
different front-end flag), or the callee's real prototype had pointer-typed
params that changed the tree walk for arg 2 only.
