## What it does
Menu text-id chooser: calls `func_181420()` for a table handle, `func_0045F910(handle)`
(handle + 0x1E0) into `func_206C20`, two `func_205050(handle, x, 1) > 0` checks, then
`func_3134A0(1, arg0, arg1[0])` / `func_312490(arg2, arg3)` gates, and a long if/else chain
over `arg0`/`arg2` vs 4, the two check flags, `arg1[0]`/`arg1[1]` (s16 loads) and the
`func_206C20` result. Each arm stores a small code (0..6) through `out` and returns a text
id 0x4B0..0x4D3.

## Key findings
- **The 5th parameter arrives in `$t0`**: both callers (`text_4600F0.s` +0x1A08,
  `text_45F930.s` +0xE0C) do `addiu $t0, $sp, N` before `jal func_00465380`, and the
  prologue has `daddu $s0,$t0,$zero` in the `jal func_181420` delay slot. The **K&R
  definition** (`s32 func_00465380(arg0, arg1, arg2, arg3, out) s32 arg0; ... s32 *out;`)
  reproduces the prologue + parameter copies **byte-exactly** (fp=arg3, s6=arg1, s2=arg0,
  s1=arg2, s0=out). A s64-prototype 5th param instead emits `dsll32/dsra32 0` around the
  copy — don't go there.
- Compare spellings that matched: `0 < val`/`0 < result` → `slt $at,$zero,$rX` + `beqz $at`
  (L4CC/L4E8/L560); `result > 0` → `bgtzl $s7` (L530 only); `chk2 == 1` → `addiu $v0,1` +
  `bne $s4,$v0`. `text_id = chk1 ? 0x4B7 : 0x4B6` at the tail must **not** be a `movz` —
  the original branches (`bnel $s4` / `beqz $s5` / shared `b; daddu $v0,$s3` stub at 0x46551C).
- The default `text_id = 0x4B0` must be a statement **after** the `func_3134A0` call (original
  puts `addiu $s3,$zero,0x4B0` in that call's delay slot); `*out = 0` before it.

## Remaining problem (why it is stuck)
Callee-saved register allocation. Original: `s0=out s1=arg2 s2=arg0 s3=handle→text_id
s4=chk2 s5=chk1 s6=arg1 s7=result fp=arg3` (frame 0xA0). With decls
`handle, result, text_id, chk1, chk2, val` CW gives `handle→s5 chk1→s4 chk2→s3` and the
two `if (func_205050(...) > 0) chkN = 1;` compile to `blez + nop + addiu` where the original
has `blezl + addiu-in-delay-slot`. Reordering the local declarations (chk1, result, text_id,
chk2, handle, val) fixed nothing: it **re-allocated the parameters too** (arg0→s3, out→s1)
and grew the function to 580 bytes; dropping `val` did the same. So the parameter allocation
is order-sensitive against the local list and I could not find a declaration order giving
the original map.
