Reads a record address out of `arg0[0]`, returns the `s16` at +0x12, or -1
when the field is 0. Everything about that is easy except the **`sltu`**:
CodeWarrior folds `record > 0` on a `u32` into a direct test of the value, so
it never materialises the 0/1 in `$v0` before branching.

Best so far (score 6 — 4 `*` lines + 8 bytes / 4), and the closest I got:

```c
s32 func_00340E10(u32 *arg0) {
    u32 record = arg0[0];
    s32 value = -1;
    if (record - 0 > 0) {
        value = *(s16 *)(record + 0x12);
    }
    return value;
}
```

compared with `>` does not compile (type mismatch).

**What would fix it:** something that keeps the comparison result as a value
in its own register while `$v1` stays the address — a `u32` `>` against a
nonzero constant that the peephole cannot turn into a branch condition, or the
shape the original really had. `notes/needs-claude/` has no idiom for
`sltu`-then-branch yet; if this gets solved it belongs in the skill.

## Solved (Claude, 2026-10-21)

C++, a `bool` compared with `false`:
```cpp
extern "C" s32 func_00340E10(Record **slot) {
    Record *record = *slot;

    if ((record != 0) != false) {
        return record->id;
    }
    return -1;
}
```
Comparing the `bool` result of `record != 0` against `false` keeps the
`sltu` value in `$v0` and branches on it; `== true` compares against 1
(`bnel` with `li 1`), and in C the same text folds to `beqz`. Committed as
`src/SLES_539.74/func_00340E10.cpp`; `tools/verify.py` needed to compile a
`.cpp` as C++ (it always wrote `f.c` before).
