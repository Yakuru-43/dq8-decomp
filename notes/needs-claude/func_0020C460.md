## What it seems to do

The 0x67E1 byte is a countdown flag, 0x67E4 its counter, 0x67EC a timer.
When the counter hits zero it clears the flag, computes
`ratio = (f32)timer / 127.0f`, stores it into slot+0x18, derives a
clamped volume from three slot fields, feeds that back as a float
fraction through `func_00372520`, and releases the entry with
`func_003727D0`. Slot is the usual `idx * 0xC0 + 0x5610` array, entry
`idx * 0x6C + 0x5790`, both via the `0x5874` index.

## Diff

`DIFF at +0x0: mine 27BDFFD0 orig 27BDFFE0` — the whole function is
offset by the prologue, so every line after `+0x00` differs. Mine opens
with a **0x30** frame and saves `$ra`, `$s0`, `$s1`; the original opens
with a **0x20** frame and saves only `$ra` and `$s0`. Everything else is
the same code shifted: the original's `$s0` is the argument register
copy (`daddu $s0, $a0, $zero`), and all its field accesses are relative
to `$s0`; mine keeps the argument in `$s1`, spends `$s0` on the
0x5874 field address, and reaches the argument's fields through a
materialised address (`addiu $a0, $s1, 0x67E1` + `sb $zero, 0x0($a0)`
where the original has `sb $zero, 0x67E1($s0)`).

So the C is right and the register allocation is wrong: one saved
register too many, and CodeWarrior picked `&arg0[0x5874]` as the value
worth spilling instead of `arg0` itself.

## What I tried

4. The `if (M2C_FIELD(arg0, u8 *, 0x67E1) = 0)` store as a byte write
   through the argument: original keeps `$s0` and uses `0x67E1($s0)`
   directly; mine materialises the address with `addiu` and stores
   through `$a0` with a zero offset.

Untouched suspicion: the original's two guard clauses probably return
from a single `if (byte != 0)` block whose second condition is a
`&&` (`if (c && --n <= 0)`-shaped), which is what would give one
epilogue, one saved register, and `bgtz` on the counter. A
`tools/permute.py --run 600` pass on this function is probably the
faster route than more hand variants.
