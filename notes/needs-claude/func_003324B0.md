## What was fixed from the m2c draft

- The draft models the 0x2E0 buffer as ~70 **separate locals** → CodeWarrior
  DCEs every store the function never re-reads → frame collapsed to 0x220 and
  1372 B vanished. **The whole sp+0x70..0x350 range must be ONE local struct**
  whose address escapes (`&buf` to ~40 callees), which pins every store. This
  is written up in the draft's failure mode and is the single most reusable
  finding: `typedef struct VBuf { ... }` member names = their sp addresses, in
  `src/SLES_539.74/func_003324B0.c`.
- Probe "mismatch" stores the draft emitted as `x |= (0 & 1)` are constant
  bit-ors: `|1,|2,|4,|8,|0x10,|0x20,|0x40,|0x80`.
- `func_00333B50` is 5-arg, `func_00337740` is 7-arg (register copies in the
  prologue reveal the hidden args).
- `(0x2DD-ish) << 0x1D >> 0x1F` default-case test written as
  `(((u32)buf.sp34D << 0x1D) >> 0x1F) == 0`.

## Walls (why it won't match in one session)

1. **Frame base shift.** Original: `sd ra,0x60(sp)`, buffer at **0x70**,
   ~0x20 bytes reserved above the buffer before the frame end. mwcc with the
   single-struct model puts `ra` at 0x70 and the buffer at 0x80 (only 0x10
   reserved above it), so the frame only lands on 0x370 by adding
   `u8 pad2DE[0x10]` *inside* the struct — which moves the buffer base by +8
   and makes every buffer-relative `lw/sw/lbu/lui-%lo` line differ. Tried
   pads 0x10/0x12/0x14; none restores ra@0x60 + buf@0x70. Unknown what the
   original reserves the extra 0x10 above the buffer for (a callee-written
   temp? nothing in the asm reads sp+0x350..0x35F). Candidates: an `s64`/
   double tail member, a second tiny local after the struct, or one of the
   ~40 callees' prototypes forcing alignment.
2. **Block placement / regalloc cascade.** With the base shift fixed the
   remaining diff is expected to be the P14/P15/P25/P31/P32 family: the
   `beql`-dispatch chain, the 16 probe blocks' out-of-line vs inline block
   order, and s-register assignment order (try swapping local declaration
   order per the skill's "saved registers follow declaration order").
3. **Switch case order** in the C must be written in the **asm test order**
   listed above (P32 idiom), not the natural numeric order; the 0x10D case
   must be the one that re-reads the count after the handler.
