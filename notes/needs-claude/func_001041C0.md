## Opus attempt 2026-10-29

**Solved in code; stopped by tooling.** The .text is byte-identical: 464 B,
every word equal to the original except relocation fields, and every
relocated opcode is the same. Checked by compiling and comparing the
`func_001041C0` section word by word against `extract/SLES_539.74.bin`. But
`tools/verify.py` prints `DATA`, so the function does **not** count as matched.

What it really is: the dead island is a **C++ `catch (...)` handler** and the
function is `ostream::flush()` (libstdc++-style). `sw $sp,0x74($fp)` /
`lw $sp,0x74($fp)` are CW's try-block sp save and restore. fp+0x60 is the
catch info that `__end__catch` (func_00101020) takes. func_00102670 is
`__throw` (`(0,0,0)` = `throw;`, and `(&RTTI, &obj, dtor)` = `throw Failure(..)`).
D_003BEF90 is `__RTTI__7Failure`, D_003DD6B0 is `__vt__7Failure`, and
func_001029C0 is `__dt__7FailureFv`. func_00106380 is the sentry ctor. The
tail is the inlined `~sentry()` (unitbuf flush, so the self-call). The island
is reached only through the exception tables, which is why no branch targets it.

Details that made the bytes line up:
- CW vtables have an 8-byte header, so `lw $t9,0x18($t9)` is the **5th**
  virtual. Declare 4 dummies and then `sync()`.
- The `andi 0xFF` / `andi 0xFFFF` after the masks come from small inline
  accessors returning `u8`/`u16`: `rdstate(u8 m) { return state & m; }`.
  The load order 3B-then-3A comes from `rdstate(exceptions())`.
- s3 = fp+0x7C (a register of its own for the message member, plus the s3
  save, which is what makes the frame 0x90) comes from `Text *t = &msg;` in
  the Failure ctor.
- `lw $a0,0x8C($fp)` in the tail, with no `addiu` first, comes from
  `Stream *o = os;` in the dtor.
- The object at fp+0x78 comes from `Text` being 8 bytes (`char *p; s32 len;`).

Why verify refuses it: `throw Failure(...)` makes the object emit RTTI
(`.rodata` `__RTTI__7Failure/9Exception`, plus `.data`/`.sdata` name strings
`@144/@164/@166`). `autodecomp.verify()` returns "data" for any `.data`,
`.sdata` or unexpected `.rodata`. Even without that, linking needs
`__throw = 0x102670`, `__end__catch = 0x101020`, `__vt__7Failure = 0x3DD6B0`,
`__dt__7FailureFv = 0x1029C0` and `__dt__9ExceptionFv` (only referenced from
`.exception`), and the `__throw` typeinfo argument is the *local* `@144`
(orig: D_003BEF90), which an alias cannot redirect. Accepting it needs a
decision on the verify tooling: let EH/RTTI sections through and map the
typeinfo. That is for the user, so I did not change verify.py.
