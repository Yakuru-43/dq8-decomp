# func_00337400 (SLES_539.74, 0x00337400, 128 bytes) — pilot P15

Guards, three calls, return what was looked up. `+0x00 … +0x1C` is byte-exact;
everything after is a block-placement difference. Same family as P14.

```
+01C  beqz  $s0, R            + daddu $s1, $a2, $zero   /* name == 0 */
+024  beql  $s1, $zero, epilogue + daddu $v0, $zero, $zero   /* window == 0 */
+02C  jal   func_333B10       + daddu $a0, $s1, $zero
+034  lw    $a0, 0x0($s2)
+038  jal   func_361360       + daddu $a1, $s0, $zero
+040  daddu $s0, $v0, $zero                            /* found */
+044  beql  $s0, $zero, epilogue + daddu $v0, $zero, $zero
+04C  daddu $a0, $s2, $zero
+050  daddu $a2, $s1, $zero
+054  jal   func_337540       + daddu $a1, $s0, $zero
+05C  b     epilogue          + daddu $v0, $s0, $zero
R(064): daddu $v0, $zero, $zero        /* one return-0 block, falls through */
epi(068): ld $ra … jr $ra
```

Mine (best of seven shapes, 132 bytes):

```
+01C  beqz  $s0, R1           + daddu $s1, $a2, $zero
+024  beqz  $s1, R1           + nop
+044  bnel  $s0, $zero, body  + daddu $a0, $s2, $zero   /* inverted! */
+04C  b     epilogue          + daddu $v0, $zero, $zero
+050  daddu $v0, $zero, $zero
+054  b     epilogue          + daddu $v0, $zero, $zero
… body …
+068  daddu $v0, $s0, $zero   /* return found, falls through */
+06C  epilogue
```

Two things differ, and both look like the same underlying rule I do not know:

1. **The original has ONE return-0 block** (`R` at 0x64) that all three guards
   reach; it falls through into the epilogue, and the two `beql`s hoist its
   `daddu $v0, $zero, $zero` into their delay slots (redirecting to the
   epilogue). Mine builds a separate return-0 block per `return 0` statement and
   they end in `b epilogue`.
2. **mwcc stole my third guard's delay slot** with the next call's argument
   setup and flipped the test to `bnel`. The original left `daddu $a0, $s2`
   where the source puts it and kept `beql` + the return value.

```c
    }

```

Tried (7 attempts): the two guards separate (`bltzl`-style, 140 B — worse, and
it inverts guard 2 to `bnel`); `name == 0 || window == 0` — **right**, that is
what makes guard 1 a plain `beqz` sharing a target with guard 2; `found != 0`
with the call inside and `return found;` after it; the same with `return 0` as
the last statement; `if (found != 0) { call } return found;`; and `-O2`
(176 B, clearly wrong). Shapes 1, 3, 4 and 5 produce byte-identical output, so
mwcc normalises the source order — the difference must be in something the
source order does not reach.

**What would fix it:** the rule for when mwcc merges `return 0;` statements into
one block, and when it lets the following call's argument setup into a guard's
delay slot. Both decide ~20 bytes here and the same thing cost P14.

## Retry 2026-10-21 (session 2, skill idioms applied) — still no

Best C now: `build/attempts/func_00337400.c` — **nested ifs with one trailing
`return 0;`** (the P33 "one return stub means nested ifs" idiom):

```c
if (name != 0) {
    if (window != 0) {
        func_00333B10(window);
        found = func_00361360(*container, name);
        if (found != 0) {
            func_00337540((s32)container, found, window);
            return found;
        }
    }
}
return 0;
```

This shape finally gets everything except **two instructions**: the frame, all
arg copies, `beqz $s0, R + daddu $s1,$a2` (guard 1 → the shared one-instruction
return-0 stub, which falls through into the epilogue, exactly like the
original), `b epi + daddu $v0,$s0`. 28/32 words identical. What is missing is
only the *form* of guards 2/3: mine are `beqz $s1, R + nop` / `beqz $s0, R +
nop`; the original is `beql $s1, $zero, epi + daddu $v0,$zero,$zero` /
`beql $s0, $zero, epi + daddu $v0,$zero,$zero` — the stub's store duplicated
into the branch delay slot with the branch retargeted past the stub.

Tried this session (attempts 8–19, all with the nested base unless noted;
`.c` and `.cpp`, prototyped and K&R externs, `-O3`):
- nested `if (x != 0)` skip guards (sA/sI/sJ/sK/sL byte-identical): beqz+nop,
  no hoist. `&&` flattening, `goto` to one `return 0`, unprototyped externs:
  no change.
- early `return 0;` guards (flat and nested, sC/sE/sM): each gets its own stub
  (140 B) AND mwcc inverts the guard to `bnel` stealing the next call's
  `daddu $a0` copy into the slot — the guard never comes out `beql + daddu
  $v0,$zero,$zero`.
- explicit `else { return 0; }` (sH): same bnel inversion, 140 B.
- guard 3 alone as early return (sN): 132 B, guard 3 inverted, guards 1/2 still
  beqz+nop.
- permuter from the m2c base: 90 s, no output, best 610.

Corpus evidence: no MATCHED function anywhere has `beql $sX, $zero, L` with a
hoisted `daddu $v0, $zero, $zero` (scanned every matched function's own asm).
The only matched sources whose asm hoists the return-0 store into a beql are
`func_001428D0` (= `char *temp_v0 = call(); if (!temp_v0) return 0; ...`) and
`func_0020D6E0` (= `if (!D_003E08D0) return 0; return func(D_003E08D0, arg);`,
tested register is the call's own $a0) — and in both, **nothing after the
guard is stealable** (the next call's delay slot is `nop`), so the scheduler
hoists from the target instead of inverting. In P15 the instruction after each
guard is the next call's arg-copy chain (`daddu $a0,$s1` / `daddu $a0,$s2`),
which is always stealable, and mwcc then picks the inversion or the plain
beqz+nop — never the hoist. That still-unwritten choice rule is the whole
wall here, and it is the same one as P14/P25 (their notes: `b epi + nop` vs
`bnel`-sink, and the daddu-at-loop-top copy sunk into the exit branch's slot).

**Ask:** what makes mwcc's scheduler fill a guard's delay slot from the branch
TARGET (beql + return-0 hoist) instead of from the fall-through or leaving it
nop? Suspected input: the IR form of the tested value (call result vs copy vs
global load) or an extern declaration we have not guessed (e.g. the callee
taking `void *` promoted arg, or a same-named declaration elsewhere in the
original TU).
