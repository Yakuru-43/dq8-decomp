## Wall

Third member of the fp-frame family (with `func_001007A0`, `func_00100880`
notes, and the P29 note for `func_00101510`). All functions that directly
call a stack-switching scheduler entry (`func_00102670`, and probably
`func_00130458`, `func_00101020`, thunks `func_00100CA0/CD0`) get the
`sq $fp` + `addu $fp,$sp` + `addu $sp,$fp` frame; every other function
(including `func_00100900`, which calls `func_001007A0`) stays sp-based.
So CW enables fp mode on a per-function trigger this compiler only shows
via `try/catch` — which also injects the `sw $sp,N($fp)` registration,
the extra s-register and the terminate block. The originals have the
frame WITHOUT the registration; `func_00100970` is the cleanest member to
attack it with because it has NO dead EH block at all.

What I found:
- **`__alloca(0)` anywhere in the body gives exactly the original frame**:
  0x40, `sq fp,0x10`, `ra 0x20`, `name` at `0x3C($fp)`, `addu sp,fp`
  epilogues, and at -O3 / -O4,p even `addu $fp,$sp` in the `bnez`/`beqz`
  delay slot (prologue identical through +0x18). It also emits
  `li 0xF; li -0x10; and; subu sp,sp,v0`, which the original does not
  have, and `if (0) __alloca(0);` is removed before the frame is chosen.
  So the original frame looks like an *alloca frame*, not an EH frame: no
  0x10 CatchInfo slot (`throw()` and try/catch both make it 0x50, with the
  info at fp+0x30). func_00100880 is 0x40 *with* CatchInfo; this one is
  0x40 without it.
- No fp from: dtor objects (inline-empty, dead-store, or out-of-line dtor:
  the dtor call is emitted but still sp-based), a class temporary passed by
  value, a variadic definition, `aligned(16)` local (ignored), `__asm__("")`,
  `setjmp` as the callee name, `#pragma exceptions off` + `throw()`, inline
  `throw()` helpers (the helper's handler is inlined with it if it calls
  something; no fp if it calls nothing), try/catch around call-free code
  (registration kept, no fp).
- `throw()` on the function plus `throw()` on every callee and on the
  function-pointer type still emits the `__unexpected` handler.
- Not tried: alloca whose size or result is used in a way the optimizer
  removes after frame layout (e.g. via an inline helper); a different
