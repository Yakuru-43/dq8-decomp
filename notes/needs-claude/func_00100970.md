   out right (`beqz`+`nop` tests, `daddu $a0,$s0` call delay slots, `b`
   stubs) — but frame -0x30, no `$fp`: everything differs from +0x0.
2. Same in `.cpp` with `try { loop } catch (...) {}` (`f970_a.cpp`,

   first call, forces `done` into `$s0/$s1` (extra `daddu` moves), and
   emits a catch/terminate call (`addiu $a0,$fp,0x40; jal ...`).
3. Variadic caller-side prototype for `func_00102670` (`f970_c.cpp`):
   no fp — variadic calls are not the trigger.
4. `throw()` on all callees, no try/catch (`f970_e.cpp`): compiles,
   no fp — exception specs alone are not the trigger.
5. try/catch + `throw()` on every callee inside the try (`f970_f.cpp`):
   still frame 0x60 + registration + terminate call. CW registers anyway.
6. Local struct with user-provided dtor: could not build — this
   mwccps2 rejects the out-of-line `void StackAddr::~StackAddr() {}`
   ("identifier expected"); would need an inline body. Not completed.

## Wall

Third member of the fp-frame family (with `func_001007A0`, `func_00100880`
notes, and the P29 note for `func_00101510`). All functions that directly
call a stack-switching scheduler entry (`func_00102670`, and probably
`func_00130458`, `func_00101020`, thunks `func_00100CA0/CD0`) get the
`sq $fp` + `addu $fp,$sp` + `addu $sp,$fp` frame; every other function
(including `func_00100900`, which calls `func_001007A0`) stays sp-based.
So CW enables fp mode on a per-function trigger this compiler only shows
via `try/catch` — which also injects the `sw $sp,N($fp)` registration,
the extra s-register and the terminate block. The originals have the
frame WITHOUT the registration; `func_00100970` is the cleanest member to
attack it with because it has NO dead EH block at all.
