## What I tried (11 attempts)
- `*(s64 *)(arg0 + 0x160)` via `char *` → aligned `ld $a1,0x160($a0)` (×2).
- `#pragma pack(1)`/`pack(4)`/`pack(push,4)` on the struct type, member at
  offset 0x160: ignored at 8-divisible member offsets. **Probe:** pack(4) IS
  honoured — `struct Probe { s32 a; s64 b; }` + `return p->b;` gives
  `ldr $v0,0x4($a0); ldl $v0,0xB($a0)`. The trigger is the member's declared
  offset %8 != 0, NOT the base pointer type.
- `__attribute__((aligned(4)))` on a struct → compiler rejects the syntax
  ("illegal struct definition"); mwccps2 has no `__attribute__` for this
  (same finding as func_0030D3B0's `aligned(1)` note).
- nested packed struct to place cmd0 at a %8==4 inner offset with outer pad
  0x15C (`struct CmdObj { s8 pad[0x15C]; struct CmdPair {s32; s64; s64;} }`):
  folded address 0x160 %8==0 → `ld` again.
- `(struct CmdBlob *)(arg0 + 0x15C)` with pack(4) `struct {s32; s64; s64;}`:
  cmd1 came out unaligned (`ldr 0xC($s0); ldl 0x13($s0)`) but cmd0 folded to
  `ld $a1,0x160($a0)`; frame grew to 0x30 with $s1 (score 22).
- `memcpy(&cmd0, arg0+0x160, 8)` with `extern void memcpy(...)`: emitted real
  `jal memcpy` + stack temps (score 30), not inlined.

## Open question
The ROM proved the address misaligned while the constant offset says aligned —
so the original type must have declared these words at offset ≡ 4 (mod 8) in
a packed layout with the +0x15C base folded in. Candidates to test: a
`#pragma pack(4)` struct whose FIRST member is the s64 pair (so a caller in
the original passed a pointer that was not 8-aligned — the alignment info was
lost through a `void *`/`char *` member), or a mwccps2 flag. Note the ROM
loads BOTH words unaligned; the family fix likely fixes CE80/D3B0/D600 too.
