## The matrix — the main unsolved bit

mat (sp+0xC0, 4×4 Catmull–Rom basis) — but the ORIGINAL computes several
entries at runtime with `neg.s`/`sub.s`/`div.s` by the 0.5f register (f2 =
mtc1 of lui 0x3F00, the same GPR `$a1` whose `sw` fills 0xE8 and 0xCC):

- 0xD4 = `neg.s` of 1.25f (lui 0x3FA0, f1) then `div.s` by 0.5 → −2.5
- 0xC0 and 0xE0 = `neg.s` of 0.25f (lui 0x3E80, f3) then `div.s` by 0.5 →
  −0.5 — ONE register stored twice (a CSE'd repeated expression)
- 0xDC = `neg.s` of the 0.5 register itself (f1 = neg.s f2) → −0.5
- 0xC8 = f1(−0.5) − f3(0.25) = −0.75 then `div.s` by 0.5 → −1.5
- plain constants otherwise: 1.0 (via `$a0`), 1.5, 2.0, 0.5 (via `$a1`), 0.

My draft wrote `-0.25f / 0.5f`, `(-0.5f - 0.25f) / 0.5f`, `-1.25f / 0.5f` as
literal expressions and **CodeWarrior folded them all** to `lui/sw` constants
(`lui 0xBFC0; sw 0xC8` etc.) — that plus a different store schedule is most
of the top-of-function diff. The original kept the divides, so its 0.5f/0.25f/
1.25f must reach the divide through something CW won't fold — a named local
(or a volatile/`.data` const, or a `const f32` referenced twice). Try:
`f32 h = 0.5f; f32 q = 0.25f; f32 r = 1.25f;` with the five entries written
as `-q / h` (twice), `-r / h`, `-h`, `(-h - q) / h` — the shared `neg.s`/f1
for 0xDC and 0xC8 argues the source negated the same variable twice.
