# func_00100500 — ctor-array runner; CodeWarrior refuses the stack-slot spill pattern

- Size 288 B + 12 pad (0x100500–0x100630), text_100500.s, `nonmatching ... 0x124`.
- factory-1 (Qwen) session 2026-10-21: 5 structural variants, not matched.

## What it is

`func_00100500(objects, construct, destroy, size, count)` — constructs `count`
objects of `size` bytes at `objects`, calling `construct(p, 1)` while `p`
advances; then a guarded teardown loop that would call `destroy(p, -1)`
backwards. Call sites (static_init.s): `func_00100500(&D_003F22D0,
func_0015C030, 0, 0x68, 2)` — `destroy` is always 0 there, and the teardown
guard `i < count_copy` is false by construction (loop 1 ends with `i ==
count`), so the teardown region is emitted but never taken. `func_00100480`
(matched, 0x100480) is the same teardown loop standalone (`destroy(p, -1)`
count times backwards) — reuse its call idiom.

## The asm facts

- 5 args: a0 objects, a1 construct (kept in `$s5`, `jalr $s5`, a1=1),
  a2 destroy, a3 size, t0 count.
- Loop 1 keeps p in `$s2`, count in `$s3`, size in `$s4`, construct in `$s5`;
  bottom test `sltu $v1,$v1,$s3` + `bnez` + delay `addu $s2,$s2,$s4`
  (NOT branch-likely), entry `sltu 0<count` + `bnez` into the body.
- The teardown region reads everything from **stack slots**: `$s1=sp+0xA0`
  (counter i, stored 0 at +0x44, loaded/stored in both loops), `$s0=sp+0x9C`
  (destroy copy), `$s6=sp+0x94` (size copy), `$s7=sp+0x98` (count copy), plus
  `lw $v1,0x90($sp)` (objects copy) for `objects + size * i`. The copies are
  stored in the prologue: `sw a0→0x90`, `sw $s4(size)→0x94`, `sw a2→0x9C`,
  `sw $s3(count)` in the delay slot of the entry branch.
- Teardown guard order: `sltu i<count_copy`+beqz, `lw destroy`+beqz,
  `lw size`+`mult a0,size,i`, `lw 0x90(sp)`, `beqz i`+delay
  `addu s2,base,prod`, then do-while `subu p,size; jalr f2(p,-1);
  lw i; addiu i,-1; bnez; sw i` (store in delay slot).
- Single epilogue stub `b 0x5FC` with `ld $ra` in its delay slot; frame
  -0xB0; `daddu` param moves; returns nothing meaningful.

## Wall

Every natural C (best draft: `build/drafts/func_00100500.c`) compiles to the
all-registers version: frame -0x80, s0-s6, no stack locals, loop-1 back edge
becomes `sltu`+`bnel` fused, teardown reads registers not memory. Tried:

1. single-variable version (`if (i < count)` after `for (i=0;i<count;i++)`,
   params reused in teardown) — 7 regs, no spill.
2. same but with separate copies `step = size; n = count;` used in the
   teardown, params in the loop — copy-propagation deletes them, identical
   output.
3. mirror of 2 (locals `n`/`step` in the loop, params in the teardown) —
   identical output (coalesced).
4. `static void Teardown(objects, size, destroy, i)` helper called under
   `if (i < count)` — CW did not inline it (emitted a real `jal`), wrong.

mwccps2 -O3 always fits the function in callee-saved regs; the original's
allocator spilled {i, destroy, size-copy, count-copy, objects-copy} to
adjacent slots and kept an address register per slot (`lw x,0($sN)` rather
than `lw x,0x9C($sp)`, except the single objects load). No plain-C form
tried forces that. It is probably not source-visible except by a live-set
shape that tips the allocator.

## Opus attempt 2026-10-26

**What it is:** MSL runtime `__construct_array` (NMWException.cp). The stack slots
are the EH guard object `__partial_array_destructor pad` at sp+0x90
{p, size, n, dtor, i}. Its inline destructor is the "teardown" (it runs on the
normal path too, which is why it is emitted even though `i == n`). The spill wall
is gone with a `.cpp` and the real class. The file's neighbours are the same TU:
0x100480 `__destroy_arr`, 0x100630 `__construct_new_array` (same guard, header words).

Best C (`.cpp`, lint silent), with `-O4,p`: **same layout, same 73 instructions,
same loop rotation and delay slots**. The only difference is which callee-saved
register holds each slot address:

```cpp
// flags: -O4,p
extern "C" {
typedef void *ConstructorDestructor;
#define CTORCALL_COMPLETE(ctor, objptr) (((void (*)(void *, short))ctor)(objptr, 1))
#define DTORCALL_COMPLETE(dtor, objptr) (((void (*)(void *, short))dtor)(objptr, -1))
class __partial_array_destructor {
private:
    void *p; u32 size; u32 n; ConstructorDestructor dtor;
public:
    u32 i;
    __partial_array_destructor(void *array, u32 elementsize, u32 nelements,
                               ConstructorDestructor destructor) {
        p = array; size = elementsize; n = nelements; dtor = destructor; i = n;
    }
    ~__partial_array_destructor() {
        char *ptr;
        if (i < n && dtor) {
            for (ptr = (char *)p + size * i; i > 0; i--) {
                ptr -= size;
                DTORCALL_COMPLETE(dtor, ptr);
            }
        }
    }
};
void func_00100500(void *block, ConstructorDestructor ctor,
                   ConstructorDestructor dtor, u32 size, u32 n) {
    __partial_array_destructor pad(block, size, n, dtor);
    char *p;
    for (pad.i = 0, p = (char *)block; pad.i < n; pad.i++, p += size) {
        CTORCALL_COMPLETE(ctor, p);
    }
}
}
```

Remaining diff (-O4,p): orig `s1=&i(0xA0) s0=&dtor(0x9C) s6=&size(0x94) s7=&n(0x98)`,
mine `s0=&i s1=&size s6=&dtor s7=&n`. Every instruction is otherwise identical.

Two more blockers for verify.py even once the bytes match: (1) CW emits the
destructor out of line too (`__dt__26__partial_array_destructorFv`, in a second
`.text` section, calling `__dl__FPv`), so verify says `LINK`, and `size` once the
link resolves. The integration needs to drop or alias that copy (find where the
game has it, maybe near 0x100630+), or verify.py needs to take only the function's
own section. (2) try_match.py reads the wrong bytes for a .cpp with several `.text`
sections (nm offsets are per section). Use a script that runs objdump on the whole
object (scratch/dump.py did that this session).

Tried (all b151 unless noted):
- `-O3` / `-O4` / `-O4,s` / `-O2,p` / `-O4 -opt speed`: right registers but
  jump-to-test loops (`b` to the test, `bnezl`), no rotation.
- `-O4,p` / `-O3,p`: rotation exactly right, registers permuted as above.
- `-O4,p -pragma "opt_strength_reduction off"` (or `opt_loop_invariants off`):
  **right registers**, but then the `i` loaded by the entry test is reused in the
  teardown (`lw a0` kept, no `lw a1,0(s1)` reload) and the loop tail keeps
  `addiu a0,v1,1`: about 8 words off. `opt_propagation`, `opt_lifetimes`,
  `opt_dead_assignments`, `opt_unroll_loops` off, `-inline deferred`: no change;
  `opt_common_subs off` loses the slot registers completely.
- No change at -O4,p: dropping `i = n`, an initializer-list ctor, the dtor defined
  out of class `inline`, `char *p` declared before `pad`, `p` advanced in the body,
  increment order swapped, a function-pointer typedef instead of `void *`, the
  TU with `__destroy_arr` placed first.
- Hand-guarded do-while loops at -O3: main loop alone gives right registers and
  rotation, but the teardown stays jump-to-test; guarding both shrinks the frame to
  0xA0 and rematerialises `&i`. Contrived anyway.
- Builds b103/b119 (same as b151), 2.4, b198/b210 (different allocation entirely).

Next look: the register permutation at -O4,p is the one thing left. Try the other
