Two facts make the range unmatchable on its own:

1. **Entered from the head's `b .L00472284`** (0x472258) with `$t4`, `$t0`,
   `$a2`, `$v1`, `$v0`, `$t3`, `$t2`, `$t1` all set up by the head and never
   set here. No argument list expresses "arrive at the loop condition with a
   live counter and a live base pointer".
2. **Called with `jal` from outside**: `0x462C90` and `0x464C48`
   (`asm/CASINO/text_4622D0.s:683,2822`) jump into the loop header directly —
   presumably with `$t4 >= 0x20` so the loop is skipped and the tail runs. So
   the pair cannot be merged into one file over `0x472220–0x472330` either:
   an external `jal` into the middle of a C function's loop is not expressible,
   and deleting the head's `b` would break the prologue.

That is why the row has **0 attempts** and `best_score` `NC` — there is no C
function whose natural compilation is this 208-byte range, so there is nothing
to score with `try_match.py --show`. Same family: P09/P27, P34, P42
(`func_00460710.md`, `func_00463E80.md`, `func_00462FB0.md`), but those four
are fall-through halves; this one also has external entries into the middle.

**What would fix it:** funcdb should flag `jal`-into-middle as a blocker
(`entry-inside`) at planning time. For the match itself, the only sound shape
would be a `// range: 0x472220 0x472330` file whose C body starts with the
prologue logic and whose loop is written so the header compiles to 0x472260,
**plus** a way to keep 0x472260 callable (an `asm`-level alias, or re-splatting
so the two `jal` sites get their own thin wrapper). Claude to decide which.
