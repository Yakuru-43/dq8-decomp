# func_001414D0 (640 B, 0x1414D0..0x141750)

Graphics/DMA packet builder in the `game_141020` family. Writes a 128-byte
packet at `*(p+0x28) + 16*(p+0x2C)`, calls `func_0014E130(p, 8, <u64>, <u64>)`,
then appends `D_003A0C40` (16-byte constant, `lq`/`sq`) + `(u32)(q << 4)` to
the writer cursor at `arg0->0x4` and advances it by 0x10.

## Key finding: hidden arguments in $t0/$t1/$t2
The function **reads $t0, $t1, $t2** (verified against the raw ROM words at
0x141660/0x14167C/0x141694: `dsll32 $a1,$t0,0` etc., autodecomp's decode is
correct) — they are never written inside the function. The values feed the
packet words at 0x40: `... | sext(t0) | sext(t1)<<16 | sext(t2)<<59`.
The only caller, `func_00141830` (jal at 0x141894), itself enters with
`sra $t0,$t0,4; sra $t1,$t1,4` (reads t0/t1 as inputs too); t2 is passed
through unmodified. Above it, `func_00141750` sets t0/t1/t2 to pointers into
its own frame (sp+0x30/+0x34/+0x4C) — so this whole family passes hot
scalars in temporaries.

I reproduced it in plain C with CodeWarrior's register-argument attribute:
`__attribute__((param_reg(8)))` / `(9)` / `(10)` on params 5-7 — probe
confirmed mwccps2 3.0.1b151 then emits `addu $v0,$t0,...` etc. See
`notes/needs-claude/func_001414D0_best.c` (not committed, rule 9). If
param_reg is judged too exotic for matched C, this family belongs to
asmfunc, not to the factory.
