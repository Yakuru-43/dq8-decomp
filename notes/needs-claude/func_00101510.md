The 0x1A4-byte block after the `b` is **unreachable**: every branch inside
it targets other blocks inside it; the only back-edge (`b .L0010153C` at
+0x15C4) sits in the block itself; nothing outside the function targets its
interior — `grep 0010154C` over `asm/` and `extract/` is empty (no jump
table, no function pointer, no external `jal` into it; unlike P09/P20/P27/
P34/P42 there is no splat entry point). So the executed function is only
"call CA0, call CD0, return".

## Why no legal C reproduces it

Statements after an unconditional branch-to-return are dead code; mwccps2
-O3 deletes unreachable code, so a source that compiles to the live path
loses the 416 bytes, and a source that keeps the body reachable loses the
bare `b`. The only shapes that make mwcc emit a body behind an
unconditional exit are the forbidden ones: `while (0) { ... }`, or
statements after `return`. `if (const0)`/`#if`-style folding removes the
body at CFG level, and a `noreturn` CD0 would also kill the `b tail`.
`func_00100CD0` is not noreturn in spirit (it is `(*D_0039CE10)()`, a
function-pointer thunk like CA0; neither pointer is ever written in the
asm — the loader installs them).

**Question for Claude:** what real source shape / `#pragma` makes
mwccps2 3.0.1b151 -O3 emit `jal <thunk>; b <epilogue>; <scheduled body>` —
i.e. keep a block alive that the flow never enters? Suspects: a
runtime-patched branch (game patches 0x101544 with a real `bnez`/`b`?), or
an mwcc DCE gap (late peephole inverting `beqz v0` after CD0 into `b`
without reclaiming the body). A single probe with the toolchain on a
3-line test would settle it.

## Opus attempt 2026-10-29

**Byte match, not committable: the lint refuses `#pragma exception_magic`.**
The "unreachable" block is a `catch (...)` handler: CW reaches it only through
the exception table (`.exceptix`/`.exception`), so it sits after the
`b <epilogue>`; the fp frame + `sw $sp,0x74($fp)` is the try bookkeeping.
The function is CW's runtime `__unexpected(CatchInfo *)`
(NMWException.cp): `try { unexpected(); } catch (...) { rethrow if the new
exception is in the spec, throw bad_exception if that is, } terminate();`.
func_00100CA0 = unexpected(), func_00100CD0 = terminate(), func_00100A40 =
__throw_catch_compare, func_00102670 = __throw (0,0,0 = rethrow),
func_00101020 = `__end__catch`, func_00101700 = bad_exception's dtor.

The C below (`.cpp`, `-O4,p`) gives identical `.text`;
`autodecomp.verify()` returns `match` with `__end__catch = 0x101020;` added to
the symbol script (scratch/verify_alias.py). tools/verify.py alone says `LINK`
because the compiler emits the call to `__end__catch` by name.

Two things block the commit, both need the user:
1. `tools/lint_contrived.py` refuses any `#pragma`. `#pragma exception_magic`
   is not a codegen switch: it is what makes `__exception_magic` (the catch's
   CatchInfo, `typeinfo` at +4 = `lw $s3,0x64($fp)`) visible, and it is in
   Metrowerks' own runtime source. Without it the file does not compile, and
   the catch's typeinfo has no other C spelling. Needs a lint exception for
   `#pragma exception_magic` (I did not use `_Pragma` to slip past the regex).
2. `__end__catch = 0x101020;` in config/symbol_addrs_SLES_539.74.txt
   (integration's job, as for `__unexpected` in the throw() idiom).

What made it match (keep for the idiom entry once committable):
- `-O4,p`: at -O3 the spec loops are bottom-tested; -O4,p gives the
  `sltu v0,zero,count; bnez` pre-test and the `v0 = 1 / 0` join of the
  inlined helper.
- each spec entry read through `union { u32 bits; char *typeinfo; }`: the
  union local is what puts the value in its stack slot (`sw $a1,0xA8($fp)`)
  and grows the frame to 0xB0.
- `ExSpec es` declared at function scope, not in the catch: puts the magic
  at 0x60 and es at 0x80.
- the three parse calls as separate statements with `p = ...; es.specs = p;`
  (nested calls / direct `es.specs =` mis-schedule the delay slots).
MH2 catalogue not needed.
