The 0x1A4-byte block after the `b` is **unreachable**: every branch inside
it targets other blocks inside it; the only back-edge (`b .L0010153C` at
+0x15C4) sits in the block itself; nothing outside the function targets its
interior — `grep 0010154C` over `asm/` and `extract/` is empty (no jump
table, no function pointer, no external `jal` into it; unlike P09/P20/P27/
P34/P42 there is no splat entry point). So the executed function is only
"call CA0, call CD0, return".

## Why no legal C reproduces it

Statements after an unconditional branch-to-return are dead code; mwccps2
-O3 deletes unreachable code, so a source that compiles to the live path
loses the 416 bytes, and a source that keeps the body reachable loses the
bare `b`. The only shapes that make mwcc emit a body behind an
unconditional exit are the forbidden ones: `while (0) { ... }`, or
statements after `return`. `if (const0)`/`#if`-style folding removes the
body at CFG level, and a `noreturn` CD0 would also kill the `b tail`.
`func_00100CD0` is not noreturn in spirit (it is `(*D_0039CE10)()`, a
function-pointer thunk like CA0; neither pointer is ever written in the
asm — the loader installs them).

**Question for Claude:** what real source shape / `#pragma` makes
mwccps2 3.0.1b151 -O3 emit `jal <thunk>; b <epilogue>; <scheduled body>` —
i.e. keep a block alive that the flow never enters? Suspects: a
runtime-patched branch (game patches 0x101544 with a real `bnez`/`b`?), or
an mwcc DCE gap (late peephole inverting `beqz v0` after CD0 into `b`
without reclaiming the body). A single probe with the toolchain on a
3-line test would settle it.
